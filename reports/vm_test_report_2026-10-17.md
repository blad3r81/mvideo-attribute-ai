# Проверка сервиса на командной VM, 17 октября 2026

Адрес демо: https://tochka-sborki-2026-team-013.hub.gigaschool.ru/  
Машина: Docker-контейнер Node.js 20, порт 8000, сеть хоста для доступа к шлюзу LLM организаторов.  
Исходный протокол: `reports/vm_acceptance.json`.

## Что проверено

После финального обновления прошли 15 сквозных сценариев: здоровье API и данные, четыре реальных SKU (смартфон, ноутбук, телевизор, футболка), двуязычный цвет и размер EU, конфликт значений, диапазон вместо точного числа, неизвестная категория, ошибочные и слишком большие запросы, цена без справочника, а также четыре сценария с переключателем LLM. Один из них проверяет, что модель не вызывается, когда в тексте нет ёмкости батареи; три сделали реальные вызовы шлюза.

Нагрузка без LLM: 100 запросов к `/api/extract` при параллельности 10; 100 ответов HTTP 200, ошибок 0. В последнем прогоне p50 = 38 мс, p95 = 134 мс, максимум = 192 мс с клиентского компьютера. Это умеренная проверка демо, а не доказательство промышленной производительности. После прогона контейнер работал, занимал около 28 МиБ памяти в простое; в последних строках его журнала ошибок не было. `node --test` на VM: 24 пройдено, 0 ошибок.

## Проверка LLM

Использован шлюз организаторов и модель `GigaChat/GigaChat-3-Pro`. На реальном ноутбуке SKU 30072074 модель завершила запрос и дала одно предложение на проверку. На ручном смартфоне она предложила ёмкость 5000 мА·ч с дословной цитатой из описания; на ручном ноутбуке вернула одно предложение. Ни одно предложение не стало автоматически принятым атрибутом. На реальном iPhone SKU 30087001 ёмкость не указана: сервис не потратил вызов модели и оставил поле пустым. Через браузер проверены выбор SKU, переключатель LLM, строка предложения с источником и JSON в модальном окне.

На раннем прогоне нашли проблему: при длинной карточке модель дважды вернула оборванный JSON. Добавлена безопасная обработка такого ответа; ни одна часть оборванного ответа не попадает в атрибуты. Следом вход модели ограничен относящимися к пропуску полями продавца, а запрос о батарее без числового основания пропускается. После исправления полный сквозной набор прошёл. Это не исключает будущие сбои шлюза: в таком случае правила продолжают работать, а статус LLM показывает причину.

## Найденные и исправленные ошибки

1. `HUAWEI` в поле продавца и `Huawei` в названии считались конфликтом. Сравнение строковых значений теперь не зависит от регистра; исходная цитата сохраняется.
2. LLM вызывалась для конфликтов, уже требующих ручной проверки. Теперь она получает только действительно отсутствующие обязательные поля.
3. LLM предлагала `Lenovo` как модель, хотя это бренд. Совпадение с найденным брендом отклоняется; числовое предложение приводится к числу и остаётся в `review`.
4. Предложения LLM находились только в JSON. Интерфейс теперь показывает их отдельными строками с цитатой и пометкой «LLM · проверить».
5. Оборванный JSON LLM раньше выглядел как общая недоступность. Теперь у него отдельный статус, а результат правил сохраняется.

## Что тесты не доказывают

В архиве нет независимого human gold и полного официального списка обязательных полей. Поэтому нельзя заявлять gold precision/recall/F1, отсутствие всех ложных срабатываний, одинаковое качество для всех 6 963 категорий и продавцов или прирост CTR/GMV. Проверка нагрузки не включает параллельный поток платных вызовов LLM. Стоимость модели зависит от длины текста; лимит шлюза команды составляет 100 ₽ в день по странице организаторов. Публичный API с `use_llm: true` может расходовать этот лимит, поэтому для массового запуска потребуется управление вызовами и бюджетом.

## Сопоставление с ТЗ и комментарием эксперта

Пайплайн использует только текстовые входы, нормализует известные значения, возвращает источник, метод, статус и эвристическую уверенность. Правила покрывают типовые случаи, модель подключается выборочно и её ответ не принимается автоматически. Размер сохраняет систему EU/US/RU/UK/INT. Категория может прийти по ID или определиться из текста; неизвестный ID API отклоняет. Для обязательных полей смартфона и ноутбука есть отдельная проверка, но окончательный перечень по всем категориям должен прийти от организаторов.

Замечание эксперта о продуктовой проработке учтено в `docs/product-review-2026-10-17.md`: описаны пользователь, цена пропуска и ложного атрибута, граница известных данных о текущем процессе и способ измерить экономический эффект. Денежную пользу мы не подменяем предположением. До финала требуется gold-разметка, замер текущей модерации, события фильтров и заказы.
