# Технический чекпоинт, 23 октября

Технический чекпоинт проходит онлайн по слотам с 17:00 до 19:30 МСК. Эксперты смотрят ветку `main` командного Gitea и могут открыть приложение на порту 8000. Запись на слот появляется на странице «Сводка» платформы. Перед звонком нужно сверить строку «Последний push в Gitea» на странице VM.

## Что показать за 3–4 минуты

1. **Задача.** Из текста карточки товара сервис выделяет обязательные характеристики и приводит значения к справочнику. Он помогает сократить ручное заполнение карточек, сохраняя спорные значения для проверки человеком.
2. **Живой сценарий.** Открыть демо VM, выбрать SKU, запустить извлечение. Показать нормализованное значение, исходную цитату, числовой балл правил, статус и причину решения. Показать один спорный атрибут и JSON для интеграции.
3. **Архитектура.** Входной текст проходит правила извлечения, нормализацию, проверку справочника и порог принятия. LLM вызывается только для пропусков и спорных полей, если включена и доступна. Её ответы проверяются по точной цитате; без доказательства поле не принимается автоматически.
4. **Проверка.** На VM завершены 50 автоматических тестов. В репозитории есть фиксированный пример из 30 карточек и 190 обязательных полей трёх категорий. Метрики правил на разметке ассистента: precision 0,890, recall 0,721, F1 0,796. Это разбор ошибок на фиксированном примере, а не независимая оценка на human gold. Самые слабые поля в нём: модель, цвет, процессор.
5. **Стадия.** Рабочий прототип доступен по веб-интерфейсу и API, пакетный вывод формирует JSON. Для оценки реальной точности и влияния LLM нужны новые карточки, согласованная схема канонических значений и независимая разметка человеком.

## Текст для выступления

«В каталоге характеристики приходят из названия, описания и полей продавца. Сейчас значимую часть таких сведений приходится искать и приводить к единому виду вручную. Пропуск мешает товару попасть в нужный фильтр, а ошибочно принятое значение вводит покупателя в заблуждение. Поэтому мы оптимизируем не число заполненных ячеек само по себе, а число значений, которые можно подтвердить исходным текстом.

Я открою реальную карточку SKU. Сервис выделяет обязательные поля по категории, нормализует их и показывает, откуда взято каждое значение. Здесь видны принятые поля, а здесь конфликт, который остаётся на проверке. Результат доступен и человеку в интерфейсе, и следующей системе в JSON. Для типовых карточек работают правила и словари. Если значение пропущено или спорно, может подключиться LLM, но её ответ проходит проверку по точной цитате. При отказе шлюза результат правил сохраняется.

Мы проверили воспроизводимость на VM: 50 автоматических тестов проходят, а пример из 30 карточек и 190 полей позволяет повторить расчёт метрик по атрибутам. На разметке, сделанной ассистентом до просмотра предсказаний, F1 правил составил 0,796. Это диагностический пример, не оценка на независимом человеческом эталоне. Особенно нужно улучшить модель, цвет и процессор. Мы не заявляем пока рост продаж или подтверждённое снижение времени работы: для этого нужен замер текущего процесса и новый human gold. Сегодня показываем работающую цепочку, её защиту от выдумывания и честно обозначаем, что предстоит измерить перед внедрением».

Если эксперт спросит о цене ошибки в рублях, не называйте произвольную сумму. Объясните механизм: неверная характеристика портит фильтрацию и требует исправления карточки; стоимость нужно считать на данных о времени модерации, количестве исправлений и пользовательском поведении, которых сейчас нет.

## Команды для эксперта

```bash
cd ~/project
docker run --rm -v "$PWD":/app -w /app node:20-alpine node --test
docker run --rm -v "$PWD":/app -w /app node:20-alpine node scripts/verify_reference.js
docker run --rm -v "$PWD":/app -w /app node:20-alpine node scripts/predict.js data/holdout_cards.json data/holdout_predictions.json --rules-only
docker run --rm -v "$PWD":/app -w /app node:20-alpine node scripts/evaluate.js data/holdout_assistant_reference.json data/holdout_predictions.json
```

В обычном API на VM модель включается настройкой `LLM_AUTO_REVIEW=1`. В небольшой пакетной проверке можно использовать `--llm --llm-limit=10`; число внешних вызовов ограничено. При отказе шлюза исходное извлечение правил сохраняется, поле остаётся на проверке.

## Вопросы, на которые стоит ответить прямо

- **Сколько ручной работы снято?** Пока нет измерения на независимом потоке. Интерфейс отделяет принятые, спорные и отсутствующие поля; эффект нужно измерить временем обработки карточки и долей ручных исправлений на новых данных.
- **Можно ли считать балл уверенностью в вероятностном смысле?** Нет. Это заданный правилами балл решения, его калибровка на человеческом эталоне остаётся задачей.
- **Доказывают ли встроенные 30 карточек качество?** Нет. Их разметил ассистент до просмотра предсказаний. Они воспроизводят расчёт и показывают слабые поля, но не заменяют независимый human gold.
- **Зачем LLM?** Она ищет кандидатов для пропусков и проверяет спорные цитаты. Вызов возможен только при наличии настроенного шлюза и может завершиться тайм-аутом. Положительный эффект на F1 пока не подтверждён.

## Резерв показа

Если шлюз LLM не отвечает, запустить демонстрацию в режиме правил и показать результат с доказательствами и JSON. Если веб-интерфейс недоступен, использовать команды выше и уже сохранённый `reports/holdout_assistant_evaluation.json`.
