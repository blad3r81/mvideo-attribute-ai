# Пайплайн извлечения

Материалы задания и 18 слайдов исходной презентации задают маршрут: текст карточки → извлечение → нормализация → мэппинг в справочник → проверка → структурированный результат → ручная обратная связь. Фото исключены условиями задачи.

## 1. Вход и справочник

Закрытый `POST /api/extract` с токеном и отдельный ограниченный демо-маршрут `POST /api/preview` принимают `card.title`, `card.description`, `card.seller_attributes` и необязательные `card.category_id`, `card.id`. Русский и английский текст можно смешивать. Категория, если она известна, направляет к одной из 6 963 записей схемы, собранной из `skus.pkl`; родительские категории дают общую группу товара. Без категории простой базлайн распознаёт смартфон, ноутбук или одежду по тексту либо воздерживается. Из `query_clicks.parquet` в извлечение не передаются запросы и клики, поскольку по условиям вход — только карточка.

Список `_search` в каталоге используется как справочник реально встречающихся фильтруемых атрибутов данной категории. Полный официальный перечень обязательных полей не передан. Обязательные поля смартфона и ноутбука взяты из задания; для остальных категорий сервис не объявляет поле обязательным без основания.

Для нового каталога путь к JSON можно задать через `CATALOG_SCHEMA_PATH`. В каждой категории `required` перечисляет обязательные ключи, а `allowed_values` хранит канонические значения и допустимые написания. Например: `{"required":["Страна"],"allowed_values":{"Страна":[{"value":"Бангладеш","aliases":["Bangladesh"]}]}}`. Если этих полей нет, сервис не предполагает их содержание. Новое значение без указанного справочника остаётся в `review`, даже если оно найдено в карточке.

## 2. Извлечение и нормализация

- Поля продавца дают буквальное доказательство `seller_attributes.<ключ>` и метод `seller_field`. Ненужные коммерческие подборки не считаются характеристиками.
- Базовые правила и словари ищут в заголовке/описании явные бренд, модель, память, экран, батарею, цвет и размер. Ключ–значение в описании сверяется со схемой категории.
- `256 GB`/`256 ГБ` превращаются в `256` ГБ; `1 TB`/`1 ТБ` — в `1024` ГБ. Десятичная запятая для диагонали меняется на точку. Цветовые варианты `red`/«алый»/«красный» дают «красный». Значение диапазона диагонали не превращается в одно точное число.
- Для одежды размер хранится объектом `{system,value}`. `EU`, `US`, `RU`, `UK`, `INT` сохраняются отдельно; преобразования между сетками без таблицы соответствий нет.
- Остальные значения остаются строками из источника, если нет подтверждённого правила нормализации, и направляются в `review`, пока нет справочника допустимых значений. Это ограничивает ложные преобразования на длинном хвосте.

## 3. Разрешение и статус

Кандидат содержит исходное значение, нормализованное значение, атрибут, поле и цитату, метод и балл уверенности. Совпадающие нормализованные значения объединяются. Разные значения одного атрибута дают `review` с обоими кандидатами. Диапазон памяти не превращается в точный объём, неизвестный цвет не принимается, а несогласованные ширина и толщина смартфона уходят на проверку. Ненайденное обязательное поле даёт `missing`; сервис не угадывает его из общих знаний о товаре. Только `accepted` можно рассматривать для публикации после калибровки порога на gold-наборе. Сейчас баллы `.95` и `.84` — эвристические, не вероятности.

## 4. Второй этап: ML / LLM

Статистический опыт с цветом (`scripts/silver_color_experiment.py`) использует `param` как слабые метки и имя товара как вход. На 60 000 строках silver-данных обычное правило дало прокси точности 0,9194 при покрытии 0,1729. Сырая ML-модель дала прокси accuracy 0,8201 и macro-F1 0,7283, но часть её ответов не подтверждается буквальным текстом. Если требовать совпадения с явным словом цвета, прокси точности 0,9676 при покрытии 0,1624. Модель не подключена к автозаполнению: независимого gold и прироста покрытия при безопасной проверке нет. Эти числа нельзя выдавать за gold-метрики.

Опциональный `src/llm.js` вызывается только по запросу для пропущенных обязательных атрибутов и проверки части спорных полей. Он требует JSON-объект, допустимое имя поля, точную цитату из входной карточки и проверяет тип/словарь значения. Даже прошедшее предложение остаётся `review`, пока нет калибровки. Когда API модели не задан, возвращается `llm.status=not_configured`, без удалённого вызова. На VM используется шлюз организаторов; затраты в рублях на карточку пока не измерены, поскольку тарифные данные не предоставлены. Публичное демо ограничивает число фактических запросов к модели в одном процессе.

## 5. Пакет, метрики, обратная связь

`scripts/build_predictions.py` соединяет каталожные поля и тексты по SKU и передаёт карточки в тот же `catalog-extractor.js`, который использует API. Выход `data/predictions_full.jsonl.gz` содержит одну строку на каждый текстовый SKU. При отсутствии каталожного предложения остаётся только доступный текст. Это показывает реальное покрытие источников, но не подменяет отсутствующие поля догадками.

Скрипты `gold_tasks.js`, `gold_to_eval.js` и `evaluate.js` готовят отдельную ручную разметку и считают per-attribute precision/recall/F1, coverage, разрезы по категориям и продавцам, macro F1 и калибровку. `traffic_rows` учитывается как прокси частоты запрос–SKU, а не как CTR. Для честной оценки нужны независимые метки всех оцениваемых полей, включая `null` при отсутствии значения. Исправления модератора скачиваются отдельным JSON и могут использоваться при следующем обновлении словарей, правил и модели. Автоматической обратной загрузки в каталог в прототипе нет.
