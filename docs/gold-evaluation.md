# Воспроизводимая проверка качества

В выданном `cu_ws.zip` нет независимой ручной разметки обязательных характеристик. Поэтому качество на **независимом human gold** сейчас не измерено. Прогнозы сервиса не используются как эталон. Поля продавца являются частью исходного текста карточки и могут служить свидетельством при разметке, но диапазон, конфликт или отсутствие точного значения не заменяются догадкой.

## Встроенный пример для проверки расчёта

В `data/holdout_cards.json` находятся 30 SKU из исходного архива, не входивших в демонстрационные 110 карточек: по 10 из категорий 761, 914 и 987. В `data/holdout_assistant_reference.json` заполнены все 190 обязательных полей по исходному тексту **ассистентом до просмотра предсказаний**. Это открытый воспроизводимый пример, а не независимый human gold: эти метки должны пройти проверку человеком перед использованием для заявления качества. Ошибки или разные трактовки названий моделей могут менять точное совпадение.

```bash
node scripts/verify_reference.js
node scripts/predict.js data/holdout_cards.json data/holdout_predictions.json --rules-only
node scripts/evaluate.js data/holdout_assistant_reference.json data/holdout_predictions.json > reports/holdout_assistant_evaluation.json
node --test
```

`verify_reference.js` проверяет отсутствие пересечения с демо, полноту всех 190 полей и баланс категорий. Отчёт о первом прогоне и известных конфликтах: `reports/holdout_assistant_audit.md`. В этих карточках есть полезные трудные случаи: у SKU 400228693 в описании указано 6,8 дюйма, а в поле `_search` — 6,56; у SKU 400489984 — 6,5 против 6,1. В обоих случаях точная диагональ размечена `null`. Для SKU 400558740 цвет в заголовке и поле `_search` расходится, поэтому цвет тоже `null`. Эти карточки не следует использовать для подбора правил, если их же планируется предъявлять как независимый тест.

24 октября добавлен второй открытый набор из 12 ранее не использованных SKU и 76 обязательных полей: `data/holdout_second_cards.json` и `data/holdout_second_reference.json`. Его можно повторить командой `npm run verify:reference:second`; подробности и результаты в `reports/holdout_second_audit.md`. Метки сделаны ассистентом до первого прогона предсказаний, но затем набор использовался для исправления ошибок. Он полезен для регрессионной проверки и демонстрации расчёта F1, однако не является независимым human gold. Оценщик считает значения одинаковыми при различии регистра, пробелов и `е/ё`; он не считает разные названия моделей или процессоров эквивалентными без явного правила нормализации.

## Подготовка эталона

Для следующей независимой проверки с разметкой людьми можно восстановить **новые** карточки из исходного архива:

```bash
python scripts/sample_holdout.py --dataset-dir work/dataset --output work/next_holdout_cards.json --exclude-cards data/holdout_cards.json
node scripts/gold_tasks.js work/next_holdout_cards.json work/next_holdout_gold_tasks.json 10 required
```

Команда отбирает следующие 30 карточек тех же трёх категорий, исключая демонстрационный и уже просмотренный ассистентом набор. Выбор по SKU детерминирован; значения для эталона не берутся из предсказаний. Исходные тексты и атрибуты продавца показываются разметчику как вход карточки, но не как готовый ответ. Эти новые файлы в `work/` не публикуются вместе с кодом. Пока люди не заполнят ответы, это **только задание**, а не независимый gold и не оценка точности. Для редких категорий укажите их ID через `--categories` только после утверждения обязательных полей в схеме. Перед ручной разметкой зафиксируйте версию кода и отобранные SKU, затем не подбирайте правила на этой выборке.

1. Для пробной ручной проверки обязательных полей смартфонов и ноутбуков выполнить `node scripts/gold_tasks.js data/real_cards.json work/required_gold_tasks.json 3 required`. В текущем демо-наборе это 9 карточек трёх категорий и 57 полей. Эти карточки уже использовались при разработке: их разметка проверяет процесс, но не даёт независимой оценки качества. Для итогового gold подайте скрипту ранее не использованные карточки. Для более широкой оценки выполнить `node scripts/gold_tasks.js data/real_cards.json work/gold_tasks.json 3 all`. Скрипт берёт список полей только из схемы кейса и отбирает карточки разных категорий и частот запрос–SKU. Ни значения, ни список полей из предсказаний в задание разметчику не попадают.
2. Разметчик заполняет каждый атрибут только по тексту карточки. Если подтверждения в тексте нет, ставит `null`. Удаляет все `__UNLABELED__`. Спорные случаи проверяет второй разметчик; расхождения разрешаются до расчёта метрик.
3. Сохранить исходное задание неизменным и выполнить `node scripts/gold_to_eval.js work/completed_tasks.json work/gold.json work/next_holdout_gold_tasks.json`. Последний аргумент проверяет, что не были выброшены трудные карточки или отдельные поля. Скрипт отклоняет незавершённые, некорректные и дублированные карточки. `work/gold.json` не следует включать в Git без разрешения владельца данных.

## Расчёт

```bash
node scripts/predict.js work/next_holdout_cards.json work/holdout_predictions.json --rules-only
node scripts/evaluate.js work/gold.json work/holdout_predictions.json > work/evaluation.json
```

Для сравнения с модельной веткой при настроенном шлюзе выполните `node scripts/predict.js work/next_holdout_cards.json work/holdout_hybrid.json --llm --llm-limit=30` и оцените тот же `work/gold.json`. Сравнивайте вместе с числом фактических вызовов, стоимостью и долей `review`; результат LLM не принимается автоматически без цитаты и допустимого значения.

Предсказания для holdout нужно строить текущей версией кода на тех же SKU, которые размечены людьми; старую демонстрационную выгрузку использовать нельзя. Скрипт считает общий micro F1, срезы по атрибутам, категориям и продавцам, macro F1 по атрибутам и категориям, покрытие и калибровку принятого значения. Малые срезы категорий помечаются отдельно; они не доказывают качество на всём длинном хвосте. При `status: "error"` у карточки пакетного прогона расчёт останавливается, чтобы сбой не выглядел как обычный пропуск.

Результат по девяти карточкам следует обозначать как предварительную проверку обязательных полей, а не как качество на всём каталоге. Для настройки порога и независимой итоговой оценки нужны разные размеченные карточки; при такой малой выборке порог лучше не подбирать.

`traffic_rows` используется только как вес частоты строк запрос–SKU. Без показов, заказов и событий фильтров нельзя вычислить CTR, GMV или денежный эффект. До независимого gold числовой `confidence` остаётся эвристическим баллом правил, а порог 0,8 — предварительной настройкой. После разметки порог нужно выбрать на одной части gold и сообщить качество на отдельной части, не используя её для настройки.
