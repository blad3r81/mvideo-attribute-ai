# Что показать, если команда выйдет в финал

## Текущая стадия

Работает цепочка от текстовой карточки до JSON: извлечение из заголовка, описания и полей продавца, нормализация, проверка значения и цитаты, статус `accepted`, `review` или `missing`, пакетная выгрузка. На VM ветка LLM вызывается для пропусков и споров при включённой конфигурации; рост точности от неё пока не доказан. В репозитории есть 42 карточки с 266 размеченными обязательными полями из трёх категорий. Разметку сделал ассистент по исходным текстам. После первого расчёта по этим карточкам код дорабатывался, поэтому метрики пригодны для внутренней проверки и рассказа об ошибках, но не являются независимой оценкой качества.

## Показ на шесть минут

1. **0:00–0:45. Проблема.** У продавцов характеристики встречаются в свободном тексте и записаны по-разному. Пропуск скрывает товар из фильтра; ошибочное значение может показать покупателю неподходящий товар. Фактическая цена ошибки у партнёра нам не передана.
2. **0:45–2:30. Обычная карточка.** Ввести текст смартфона с явно указанными памятью, диагональю и батареей. Показать в результате исходную цитату, нормализованное значение и статус. Открыть JSON и указать, что каталог берёт только подтверждённые поля.
3. **2:30–3:45. Спорная карточка.** Взять один заранее проверенный пример с конфликтующими значениями диагонали или цвета. Показать `review` и причину конфликта. Объяснить, что значение не записывается автоматически, даже если модель предложила ответ.
4. **3:45–4:45. Техника.** На одной схеме устно пройти: схема категории → правила и поля продавца → нормализация и справочник → необязательная LLM для сложных случаев → постпроверка цитаты и порог → JSON/экспорт.
5. **4:45–6:00. Измерения и ограничения.** Показать команду повторения расчёта `npm run verify:reference:second` и таблицу per-attribute. Сказать: на 12 внутренних карточках F1 0,894 после исправлений; это не результат на независимом human gold. Следующий шаг: новые SKU, согласованная разметка и измерение доли ручной проверки, времени и цены вызовов.

Для живого показа держать заранее открытый сервис на VM и резервный локальный запуск по README. После стоп-кода новый код опубликован только в GitHub; VM и официальный Gitea могут оставаться на версии 23 октября. Перед показом сверить `git rev-parse --short HEAD` с нужной версией и не выдавать старый сервис за результат новых правок. Экспертскую карточку вставлять без изменения текста: если нужного значения нет, `missing` является корректным безопасным ответом. Если LLM-шлюз недоступен, показать работу правил и статус недоступности ветки, не обещая ответ модели.

## Четыре технических вопроса, к которым стоит подготовиться

- **Откуда берётся уверенность?** Пока это оценка силы правила и источника, порог задаётся конфигурацией. Она ещё не откалибрована на независимом gold и не является вероятностью ошибки.
- **Почему не отдаёте всё LLM?** Правила и справочник быстро покрывают типичные явные значения. LLM вызывается для пропусков и споров; её предложение проходит строгую проверку формата, цитаты и допустимого значения. На проверенных 30 карточках вызовы не дали новых автоматически принятых значений.
- **Как защищаетесь от выдумывания?** Принятому атрибуту нужна цитата из входного текста, соответствие типу и словарю, отсутствие конфликта и достаточный порог. Иначе `review` или `missing`.
- **Как доказана точность?** Сейчас есть воспроизводимый внутренний пример и F1 по атрибутам и категориям. Независимого результата нет. Для него нужны новые карточки, фиксированная версия кода и разметка, не использованная для разработки.

## Что доделать после решения о финале

1. Согласовать с владельцем кейса обязательные поля и каноническое название модели для каждой выбранной категории.
2. Получить новую выборку и независимую разметку. Разделить настройку порога и итоговую оценку.
3. Разобрать карточки с загрязнённым описанием другого товара, например SKU `401249650`: часть полей сервис пока принимает, хотя источники противоречат друг другу.
4. Измерить на настоящем процессе долю карточек, требующих ручной проверки, время модерации и цену ошибок. Без исходных данных не обещать денежный эффект.
