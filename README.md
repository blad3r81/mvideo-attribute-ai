# М.Видео: заполнение характеристик товаров по тексту карточки

Это продуктовый бриф для чекпоинта 15 октября 2026 года. Мы работаем над сервисом, который помогает приводить карточки продавцов к единому формату каталога. Сейчас можно открыть [работающий прототип](https://mvideo-attribute-ai.vercel.app/) в браузере и проверить извлечение на реальном SKU или на своём тексте.

[Продуктовый бриф в PDF](product-brief-checkpoint.pdf) содержит 10 слайдов. В нём есть ответы на пять вопросов чекпоинта и снимки прототипа на слайдах 6 и 7.

## 1. Какую задачу решаем и кто будет пользоваться сервисом

Продавцы передают название, описание и собственные поля товара в разном виде. Одни характеристики указаны только внутри описания, другие записаны по-разному, а часть полей вообще пуста. Из-за этого карточка хуже участвует в фильтрах поиска и сравнении товаров. Ошибочно заполненное поле тоже опасно: покупатель может получить товар, который не соответствует выбранному фильтру.

Наша задача состоит в том, чтобы извлечь из входного текста подтверждённые характеристики и подготовить их для каталога. Сервис не должен заполнять поле только потому, что значение выглядит правдоподобным. Если записи противоречат друг другу или значение не найдено, это видно в результате.

Основной пользователь на текущем этапе — специалист каталога или модератор. Он видит значение, исходный текст, поле, из которого оно получено, и причину, по которой значение принято или отправлено на проверку. Продавец может использовать тот же результат при создании карточки и исправить недостающие данные. Покупатель не работает с этим интерфейсом напрямую, но получает пользу от более полного и аккуратного каталога.

## 2. Какие требования и ограничения учитываем

На вход подаются только название, описание и атрибуты продавца. Категорию можно передать, но она не обязательна. Изображения в этом задании не используются. На выходе сервис возвращает JSON и показывает таблицу. Для каждого поля есть нормализованное значение, фрагмент подтверждающего текста, источник, метод извлечения, оценка уверенности и статус: `accepted`, `review` или `missing`.

Для смартфона проверяются бренд, модель, память, диагональ экрана, ёмкость аккумулятора и цвет. Для ноутбука проверяются бренд, модель как общее поле, процессор, оперативная память, накопитель, диагональ и цвет. Эти наборы составлены по примерам из задания. Официального перечня обязательных атрибутов для всех категорий в архиве нет, поэтому мы не называем его завершённым.

Правила приводят типовые записи на русском и английском к общему виду. Например, `256 GB` и `256 ГБ` относятся к одному объёму памяти. Цвета также нормализуются. Системы размеров EU, US и RU сохраняются отдельно, чтобы не потерять исходный смысл размера. Значение сверяется со справочником атрибутов категории и с текстом карточки. Конфликт не публикуется автоматически.

Архив содержит 1 177 200 SKU с текстом, 546 069 предложений с параметрами каталога, 30 991 350 строк запрос–SKU и таксономию из 6 963 категорий. Это масштаб входных данных, а не показатели качества. В архиве нет независимой ручной разметки, показов поиска и событий использования фильтров. Поэтому мы пока не заявляем gold F1, CTR или рост GMV. Китайский текст без структурированных полей также не проверен достаточно хорошо, чтобы обещать качество для него.

## 3. Как устроен основной сценарий

Пользователь выбирает товар из предоставленного архива или вводит собственную карточку. Сервис определяет схему категории, ищет явные значения в полях продавца и описании, нормализует единицы и варианты записи, затем проверяет доказательство для каждого кандидата. Результат появляется в таблице. Оттуда можно открыть JSON для интеграции через `POST /api/extract`.

Мы начали с правил и словарей, потому что они быстро обрабатывают типовые случаи и позволяют показать, почему получено значение. В прототипе есть отдельный эксперимент с моделью для цвета. Он пока не используется как основной путь. LLM предусмотрена для сложных пропусков, но сейчас не настроена. Даже после подключения её предложения должны проходить проверку схемы и подтверждения во входном тексте.

На SKU 30079343 сервис принимает пять из шести обязательных полей смартфона. Модель отправляется на проверку, потому что в карточке есть несколько несовпадающих записей. Это пример работы маршрута проверки, а не оценка точности на всём каталоге.

Предполагаемый рабочий цикл заканчивается не на выдаче JSON. Исправления модератора должны возвращаться в разметку и словари, чтобы типовые ошибки исправлялись в следующих версиях. Для полноценного цикла нам нужна независимая разметка и процесс её обновления.

## 4. Какую ценность получают пользователь и бизнес

Модератору не нужно искать каждую характеристику по всему описанию: рядом с результатом уже показано подтверждение и источник. Продавец видит, какие важные поля удалось заполнить, а какие требуют уточнения. Для М.Видео это путь к более полному каталогу, который лучше подходит для фильтров, сравнения, рекомендаций и сопоставления одинаковых товаров.

Мы пока не превращаем эту пользу в обещание конкретного роста продаж. Для такого вывода нужно измерить качество заполнения на независимой разметке, затем проверить влияние на реальные сценарии поиска. Текущий результат показывает, что технический сценарий работает и что спорные значения можно отделить от подтверждённых.

## 5. По каким метрикам будем понимать, что решение работает

Основные метрики качества — precision, recall и F1 отдельно для каждого атрибута на наборе, размеченном людьми. Общая accuracy не покажет провал на редком поле, поэтому одного среднего числа недостаточно. Дополнительно считаем coverage: какую долю карточек удалось корректно заполнить. Результаты смотрим отдельно по категориям, включая редкие, и по продавцам разного размера.

Для продуктовой оценки важно понять, какие поля действительно используются в фильтрах. Такие атрибуты должны иметь больший вес при выборе приоритетов. В предоставленных кликах есть частота строк запрос–SKU, но нет показов и событий фильтрации. Поэтому клики можно использовать только как ограниченный сигнал приоритета, не как CTR и не как прямое доказательство бизнес-эффекта.

## Стадия проекта и материалы

Сейчас работают веб-интерфейс, JSON API, правила, нормализация и пакетная обработка. В интерфейсе доступны 110 реальных SKU из архива. Подготовлен пакет предсказаний по 1 177 200 SKU. Автоматические проверки правил проходят 8 из 8. Уверенность правил остаётся эвристическим баллом, а не откалиброванной вероятностью.

Следующий шаг после чекпоинта — получить официальный список обязательных полей и независимый набор ручной разметки. На нём мы сможем измерить качество по каждому атрибуту и настроить пороги автоматического принятия и ручной проверки.

В этом публичном репозитории размещены README, PDF-бриф и [текст для платформы](platform-description.md). Исходный архив карточек и производные выгрузки сюда не загружены. Прототип доступен по [публичной ссылке](https://mvideo-attribute-ai.vercel.app/); полный рабочий проект и сценарии подготовки данных находятся в локальной рабочей папке команды.
