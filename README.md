# М.Видео · извлечение характеристик товаров

Рабочий прототип по архиву `cu_ws.zip`. Вход: название, описание, атрибуты продавца и необязательный ID категории. Выход: JSON со значением, нормализацией, источником, методом, эвристической уверенностью и статусом `accepted` / `review` / `missing`. Изображения не используются.

Публичное демо: [mvideo-attribute-ai.vercel.app](https://mvideo-attribute-ai.vercel.app/). [Продуктовый бриф для чекпоинта](https://mvideo-attribute-ai.vercel.app/product-brief-checkpoint.pdf) содержит 10 слайдов, ответы на пять вопросов и снимки работающего прототипа в ПК-версии.

Версия с доработками к 23 октября работает на [VM хакатона](https://tochka-sborki-2026-team-013.hub.gigaschool.ru/); здесь настроен шлюз LLM организаторов. Vercel показывает более раннее демо. [Командный Gitea](https://git.hub.gigaschool.ru/tochka-sborki-2026-team-013/project) содержит официальный снимок `main` до стоп-кода 23 октября. В этом GitHub опубликованы последующие материалы для технического чекпоинта; они не меняют официальный снимок.

Для экспертов: [сценарий показа на шесть минут](docs/demo-runbook-2026-10-23.md), [краткий технический рассказ](docs/technical-checkpoint-2026-10-23.md), [актуальное описание решения](platform-description.md), [проверка метрик и ограничений](reports/holdout_assistant_audit.md).

## Быстрый запуск

Требуется Node.js 20 или новее. Для запуска сайта зависимости npm не нужны.
Параметры окружения перечислены в [`.env.example`](.env.example). Node.js не читает этот файл автоматически: задайте переменные в терминале или в системе развёртывания. `POST /api/extract` всегда требует `API_TOKEN` и заголовок `Authorization: Bearer <токен>`. Без токена закрытый API отвечает 503. `DEMO_MODE=1` включает отдельный публичный `POST /api/preview` для интерфейса: вход ограничен 100 КБ и 60 запросами в минуту на адрес клиента в одном процессе. Публичный маршрут не снимает защиту с `/api/extract`; глобальный лимит LLM задаётся `LLM_DAILY_LIMIT`. Для промышленного многопроцессного запуска лимиты и аутентификацию необходимо перенести в общий шлюз.

```powershell
cd C:\путь\к\mvideo-attribute-ai
$env:DEMO_MODE='1'
node scripts/check_setup.js
node src/server.js
```

Откройте [http://127.0.0.1:4174](http://127.0.0.1:4174). В интерфейсе доступно 110 настоящих SKU, найденных одновременно в каталоге, описаниях и кликах. Можно ввести свою карточку, выбрать товар в поисковом списке, отфильтровать атрибуты и открыть JSON в модальном окне. Маршруты: закрытый `POST /api/extract`, публичный только при `DEMO_MODE=1` `POST /api/preview`, `GET /api/health`, `GET /api/stats`, `GET /api/schema?category_id=914`, `GET /api/demo?q=...`.

После запуска выполните `node scripts/smoke.js` в другом терминале. Проверка берёт первые доступные демонстрационные карточки, а также отдельную текстовую карточку и ошибочные запросы. Она не зависит от конкретных ID демонстрационных SKU. Если API закрыт токеном, задайте тот же `API_TOKEN` в терминале проверки. `scripts/vm_acceptance.js` отдельно проверяет известные SKU именно выданного архива и не служит универсальным тестом нового набора данных.

| Среда | Адрес | Настройка |
|---|---|---|
| Локальный запуск | `http://127.0.0.1:4174` | `DEMO_MODE=1`, затем `node src/server.js` |
| VM хакатона | Публичный адрес команды, внутри VM `http://127.0.0.1:8000` | Dockerfile устанавливает `HOST=0.0.0.0`, `PORT=8000`; запуск в `docs/vm-deployment.md` |
| Закрытый API | Адрес выбранного развертывания | `API_TOKEN`, заголовок Bearer; действует и при `DEMO_MODE=1` |

Пример API:

```powershell
$card = @{card=@{title='Смартфон Samsung 256 GB black';description='Экран 6,7 дюйма';seller_attributes=@{Цвет='black';'Объём памяти'='256 GB'}}} | ConvertTo-Json -Depth 8
Invoke-RestMethod http://127.0.0.1:4174/api/preview -Method Post -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($card))
```

`confidence` — заданный правилами балл, не калиброванная вероятность. `decision_policy` в JSON указывает порог автоматического принятия и тип оценки. Значение принимается только при балле не ниже порога, наличии цитаты и прохождении проверки формата или справочника; `reason` объясняет решение. Конфликты и пропуски не публикуются автоматически. Настройки порога и словари находятся в `config/decision_policy.json` и `config/lexicon.json`. При `LLM_AUTO_REVIEW=1` настроенная LLM включена в обычный путь API и по умолчанию выбрана в форме VM; `use_llm: false` отключает её для конкретного запроса. Без этого флага модель вызывается только при `use_llm: true`. Она предлагает значения для обязательных пропусков и проверяет до 20 спорных полей за запрос. Ответ модели сверяется с точной цитатой исходной карточки; результат проверки записывается в `llm.review_checks`. Без справочника допустимых значений поле остаётся в `review`. Сам Codex как локальный API в прототип не встроен.

Для небольшого пакетного прогона та же модельная ветка доступна через `node scripts/predict.js cards.json predictions.json --llm --llm-limit=10`. При `LLM_AUTO_REVIEW=1` она включается и без `--llm`; `--rules-only` даёт воспроизводимый базовый результат. Лимит ограничивает число фактических внешних вызовов, отказ модели сохраняет результат правил и отмечается в `llm.status`. Пакетный вызов ждёт до 30 секунд, если `LLM_TIMEOUT_MS` не задан явно; интерактивный API сохраняет свой отдельный тайм-аут. Потоковая выгрузка большого каталога `scripts/predict_stream.js` остаётся на правилах: запуск модели на каждом из 1,17 млн SKU не обоснован по стоимости. Для сравнения качества правила и гибрид должны оцениваться на одинаковых карточках и одинаковой разметке.

В интерфейсе спорный кандидат можно подтвердить или отклонить, принятое поле пометить ошибочным, а для пропуска предложить значение. Решения скачиваются отдельным файлом для разметки: исходный JSON предсказания и каталог не меняются автоматически, а предложенное человеком значение не публикуется без проверки. Пояснение статусов, причины решений и порог принятия находятся рядом с таблицей. Публичный предпросмотр ограничен 100 КБ, закрытый API — 1 МБ; проверяются типы, длины и структура полей. Ошибки внешней LLM оставляют результат правил доступным. Таймаут запроса к модели задаётся `LLM_TIMEOUT_MS`.

### Запуск на VM хакатона

Для командной VM подготовлен `Dockerfile`: установленный там Docker запускает Node.js 20 внутри контейнера. Сервис слушает `0.0.0.0:8000`, как требует публичный адрес демо. Команды запуска, проверки и сдачи кода приведены в `docs/vm-deployment.md`. Ключ LLM не хранится в репозитории: на VM используются предоставленные организаторами `OPENAI_BASE_URL` и `OPENAI_API_KEY`, а модель задаётся отдельно через `LLM_MODEL`. На VM модель включается по умолчанию через `LLM_AUTO_REVIEW=1`; без доказательства или допустимого значения она не публикует характеристику автоматически. Лимит вызовов ограничивает стоимость.

Точные диапазоны не превращаются в одно число. Неизвестный цвет, подозрительно несогласованные размеры и значения атрибутов без справочника допустимых значений получают `review`. Неверный `category_id` отклоняется API с кодом 400. Правила и статусы проверяются командой `node --test`. Сквозные проверки VM: `node scripts/vm_acceptance.js --llm`. Результат последнего прогона: `reports/vm_acceptance.json`.

## Состав решения

Чтобы передать запускаемый код одним файлом, выполните `python scripts/package_code.py`. Архив кода включает UI, API, скрипты, тесты, схемы и демонстрационные карточки. Большая выгрузка `data/predictions_full.jsonl.gz` хранится отдельно и воспроизводится командой ниже. Распаковка входного архива проверяет список и тип файлов, размер и CRC; неполные результаты пакетного прогона не заменяют готовую выгрузку. В потоковом прогоне единичная ошибка карточки записывается отдельной строкой со `status: "error"`; число ошибок фиксируется в `reports/prediction_run.json`. Если не обработана ни одна карточка или нарушена целостность вывода, готовая выгрузка не заменяется. Gold-оценка отказывается считать метрики по карточке с ошибкой.

| Артефакт | Где находится |
|---|---|
| Воспроизводимый код | `src/`, `scripts/`, `test/` |
| Инструкция | Этот README |
| EDA | `reports/eda_dataset.md`, `data/dataset_stats.json` |
| Пайплайн | `docs/pipeline.md`, `src/catalog-extractor.js` |
| Предсказания | `data/real_predictions.json` — проверяемый пример для 110 реальных SKU. Полная выгрузка для 1 177 200 SKU создаётся скриптом `scripts/build_predictions.py` в `data/predictions_full.jsonl.gz` и из-за размера не хранится в Git. |
| Презентация на продуктовом чекпоинте | `presentation/product-brief-checkpoint.pdf`; интерактивная версия открывается по `/presentation`. Финальная презентация готовится к заключительному этапу. |

Продуктовый бриф для чекпоинта лежит в `presentation/product-brief-checkpoint.pdf` и доступен в демо по `/product-brief-checkpoint.pdf`.

`data/real_cards.json` — 110 реальных карточек для проверки UI. Оригинальный архив не копируется в проект. Структура категорий и имена атрибутов извлечены из `skus.pkl` безопасным разбором opcodes, без `pickle.load`.
Демонстрационные карточки не участвуют в логике извлечения. Для другого набора можно указать `CATALOG_SCHEMA_PATH`, `DEMO_CARDS_PATH`, `DATASET_STATS_PATH` в том же формате. В объекте категории допускаются `required` (ключи обязательных полей) и `allowed_values` (справочник канонических значений и вариантов написания). Правила синонимов вынесены в `config/lexicon.json`, порог решения — в `config/decision_policy.json`; их пути можно задать через `LEXICON_PATH` и `DECISION_POLICY_PATH`. Извлекателю также можно передать каталог как зависимость без смены глобальных файлов. Пример схемы и ограничения описаны в `docs/pipeline.md`. Официальный список обязательных полей и gold-разметка по-прежнему нужны для достоверной оценки на новом каталоге.

## Воспроизведение из исходного архива

### Проверка метрик на встроенном примере

В репозитории есть 30 карточек трёх категорий и разметка всех 190 обязательных полей, сделанная ассистентом по исходному тексту до просмотра предсказаний. Для быстрого повторения запустите `npm run verify:reference`; подробные результаты первого прогона находятся в `reports/holdout_assistant_audit.md` и `reports/holdout_assistant_evaluation.json`. Это проверка работы оценщика и анализ ошибок на фиксированном примере, **не независимая оценка качества на human gold**. Модель и цвета на этом примере требуют отдельного внимания. Для доказательства качества на редких значениях нужна разметка новых карточек людьми; её порядок описан в `docs/gold-evaluation.md`.


Требуются Python 3.11+, `python -m pip install -r requirements.txt`, Node.js 20+, около 5 ГБ свободного места. Команды выполнять в корне проекта. Путь к архиву задаётся явно.

```powershell
python scripts/prep/extract_dataset.py --archive 'C:\путь\к\cu_ws.zip'
python scripts/prep/parquet_eda.py
python scripts/prep/select_examples.py
python scripts/prep/pickle_refs.py
python scripts/prep/process_catalog.py
python scripts/prep/build_initial_config.py
python scripts/prep/finalize_data.py
python scripts/build_predictions.py --dataset-dir work/dataset
python scripts/analyze_predictions.py
python scripts/silver_color_experiment.py --offers work/dataset/offers_compact.jsonl.gz
node --test
```

Для независимой проверки отберите **новые** ранее не использованные карточки по инструкции в `docs/gold-evaluation.md`. Встроенные 30 SKU уже просмотрены при разметке ассистентом, поэтому их нельзя представлять как независимый human gold. Список полей берётся из схемы кейса, предсказания сервиса разметчику не показываются. Разметчик заполняет поля по исходному тексту, ставит `null`, если подтверждения нет, и удаляет маркер `__UNLABELED__`. После ручной проверки выполните `node scripts/gold_to_eval.js work/completed_tasks.json work/gold.json work/next_holdout_gold_tasks.json`, затем постройте предсказания текущим кодом именно для этих SKU и запустите `node scripts/evaluate.js work/gold.json work/holdout_predictions.json`. Исходный файл заданий служит проверкой полноты: трудные карточки и поля нельзя убрать незаметно. Не используйте собственные предсказания как gold. Скрипт считает общий micro F1, precision/recall/F1 и coverage по атрибутам, категориям и продавцам, macro F1, калибровку уверенности и показатели с весом `traffic_rows`. Малые срезы категорий помечаются отдельно. Число кликов служит только прокси частоты и не позволяет считать CTR или GMV. До независимой ручной разметки такие метрики не заявляются.

На Windows с проблемной кодировкой запускайте Python с `-X utf8`. Полный разбор большого pickle занимает несколько минут. Скрипт `build_predictions.py` создаёт `work/dataset/offers_index.sqlite` для пакетного соединения по SKU. Переоценка модели цвета на структурированных значениях каталога даёт только silver-метрики, а не независимый gold.

## Как устроена проверка

1. Справочник: 6 963 категории и атрибуты с суффиксом `_search` из каталога; родительская категория помогает распознать смартфоны и ноутбуки.
2. Правила/словари: явные поля продавца, ключ–значение в описании, конвертация `GB/ГБ`, `TB/ТБ`, цветов, десятичной запятой и размерных систем.
3. Необязательный ML-эксперимент: статистическая модель цвета на silver-метках; без буквального подтверждения предсказание не принимается. Результаты — `reports/silver_color_experiment.json`.
4. Необязательная LLM: предлагает недостающие обязательные поля и проверяет цитаты для спорных значений; строгий JSON, сверка с исходным текстом и сохранение `review`, если нет справочника допустимых значений.
5. Порог и маршрут: принимаются проверенные по типу и канонической нормализации непротиворечивые значения. Поля без справочника допустимых значений, конфликты и подозрительные размеры уходят на проверку; ненайденные обязательные поля остаются пустыми.

Реального списка обязательных атрибутов для всех категорий и независимой ручной разметки в архиве нет. Из задания известны примеры для смартфона и ноутбука. Поэтому gold precision/recall/F1, бизнес прирост GMV, CTR и денежная стоимость LLM на карточку **не заявляются**. Клики без показов дают лишь частоту пар запрос–SKU; используем её как прокси для приоритета проверки, не как CTR.

### Обязательные поля и текущая стадия

| Категория | Поля из задания | Что реализовано |
|---|---|---|
| Смартфон | Бренд, модель, память, диагональ, батарея, цвет | Все шесть проверяются; конфликт модели у SKU 30079343 получает `review`, остальные пять принимаются по тексту |
| Ноутбук | Бренд, процессор, ОЗУ, накопитель, диагональ, цвет | Все перечисленные поля проверяются; модель также проверяется как общее обязательное поле |

Это проверка работы пайплайна на примерах, а не доказательство качества на всём каталоге. Веб-интерфейс, API, правила, нормализация и пакетный прогон работают. ML цвета пока экспериментальный. LLM подключена на VM через шлюз организаторов: она предлагает пропущенные значения и проверяет цитаты для спорных полей, но не принимает их автоматически без справочника; в Vercel она не настроена. Официального списка полей для всех категорий, независимого human gold, показов и событий фильтров нет. Следующая веха: получить эти данные, оценить precision/recall/F1 и coverage отдельно по атрибутам, редким категориям и продавцам и настроить пороги публикации.

### Продуктовая проверка

Текущая боль из кейса: характеристики из карточек продавцов часто остаются в свободном тексте или записаны по-разному. Для покупателя пропуск означает отсутствие товара в фильтре; ошибочно принятое значение может показать неподходящий товар. Оба типа ошибки важны, поэтому сервис отдаёт `missing` и `review`, а не заполняет поле догадкой. Нынешний сценарий: карточка поступает от продавца, сервис извлекает и нормализует значения, затем каталог может принять проверенные поля и направить сомнительные модератору. Фактические затраты времени модераторов и доля ошибок существующего процесса нам пока не переданы.

Цена ошибки в рублях пока не измерена: в данных нет показов, событий фильтров, заказов и стоимости ручной проверки. Частота строк запрос–SKU помогает определить, какие товары и поля проверять раньше, но сама по себе не равна CTR или GMV. Для оценки пользы нужны независимая разметка, число показов и кликов по фильтрам, а также измерение времени на проверку одной карточки. Разбор замечания эксперта: `docs/product-review-2026-10-17.md`; протокол проверки VM: `reports/vm_test_report_2026-10-17.md`; план показа 18 октября: `docs/rehearsal-2026-10-18.md`.

Подробности по качеству, ограничениям, пяти точкам зрения и тестам: `reports/eda_dataset.md`, `docs/analysis.md`, `docs/pipeline.md`, `reports/test_report.md`.
